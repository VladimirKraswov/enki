# Задание разработчику Enki 2.0

Развивай Enki как приложение с единственным встроенным Enki Runtime —
закреплённым Pi SDK на встроенном Node. Рабочие договорённости проекта прочитай
в `AGENTS.md`, актуальном верхнем блоке `.pi/TASK.md`, `README.md` и релевантном
разделе `ROADMAP.md`. Старые checkpoint-задания сами по себе не поручение.
Пиши пользователю по-русски, фиксируй фактические результаты и ограничения.

1. Уточни текущее состояние Git, исходную версию, точный commit и незавершённые
   изменения. Сохрани чужую работу. Составь короткий план с критериями приёмки;
   checkpoint обновляй на смысловых этапах, чтобы продолжить после compaction.
2. Прочитай [архитектуру](ARCHITECTURE.md), [контракт бэкенда](AGENT-BACKENDS.md)
   и нужные исходники. UI вызывает `AgentBackend` через `src/agent/runtime/`;
   исполнение, сессии SDK, очередь, таймеры, вопросы и разрешения принадлежат
   `src-tauri/resources/agent/`. Нативный супервизор владеет своим runtime и
   деревом процессов. Не создавай второй цикл агента или второе хранилище чатов.
3. Используй текущие настройки/ключи Enki Runtime, Hub-каталог и общий реестр
   MCP/навыков. Не требуй установленного OpenCode/Pi CLI, не меняй их глобальные
   файлы и службы, не подменяй модель и не трогай inference-VM без поручения.
   Внешние истории читаются из проверенного архива; продолжение создаётся явно
   в новом чате с происхождением, без повторного исполнения старых инструментов.
4. Делай законченный вертикальный срез: поведение, UI, обработка ошибок и
   восстановление. При смене чата/хоста сохраняй идентичность запроса; после
   потерянного подтверждения сверяй журнал, а не отправляй промпт повторно.
   «Полный доступ» соблюдай через общую политику runtime; новые инструменты
   интегрируй в неё, не обходи проверку внутри инструмента.
5. Добавляй содержательные проверки исправляемого поведения и сохранения
   соседних возможностей. Используй собственные временные проекты, профили,
   порты и синтетические данные. Реальные пользовательские чаты, ключи и
   провайдеры не являются тестовыми фикстурами. Не ослабляй утверждения ради PASS.
6. На точном изменённом исходнике выполни обязательные гейты затронутой части:
   `npm run sdk:check`, typecheck ядра, `npm run test:runtime` (Vitest и guarded
   Node SDK-набор), `npm run test:runtime-artifact`, frontend tests/build и
   `check:architecture`; для Rust — fmt/check/Clippy `-D warnings` и тесты с
   `--locked`. Полный список релизных/платформенных проверок задан в
   [SDK-UPGRADE.md](SDK-UPGRADE.md), CI и [PLATFORMS.md](PLATFORMS.md).
   Длинные команды ограничивай и показывай прогресс; сохраняй исходный сбой,
   причины повторной проверки и настоящий код завершения.
7. Изменение SDK делай отдельным сопровождаемым шагом по
   [SDK-UPGRADE.md](SDK-UPGRADE.md): точная целевая версия, обзор API, согласованные
   пины и lockfiles, проверка приватной границы совместимости, реальные тесты
   расширений/сессий и парного отката. Не ставь `latest` и не обновляй ядро в фоне.
8. Для выпуска из «Мастерской» после содержательных проверок и ревью используй
   канонический путь [обновлений Hub](HUB-UPDATES.md): чистый проверенный commit,
   `npm run release:local -- stable` (либо явно выбранный preview). Этот вход
   запускает релизные гейты перед издателем. Публикуй только авторизованный
   результат, сохрани квитанцию исходного SHA/подписанных пакетов и проверь
   реально выдаваемое обновление. Не обходи отказ публикации ручной записью в Hub.
9. Проверь затронутый сценарий в собранном Enki и поддерживаемых CI-платформах.
   Сборка, unit PASS и реальная приёмка приложения — разные результаты.
   Обнови документацию и checkpoint, укажи commit, версии, команды, артефакты,
   ограничения и то, что не проверено. Не заявляй DONE или выпуск при красном
   обязательном гейте, неустановленном пакете или неподтверждённой публикации.

Системный application ID, идентичность хранилищ и механизм миграции сохраняй.
Не переписывай старые транскрипты и не удаляй данные ради «чистого старта».
Установка/перезапуск ждут штатного простоя и согласованного восстановления
работы. Останавливай только принадлежащие Enki процессы, по подтверждённой
идентичности, а не по общему имени процесса.
