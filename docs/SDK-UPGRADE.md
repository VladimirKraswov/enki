# Обновление ядра Pi SDK (явная целевая версия)

Каноническая страница процесса. Ядро Enki — встроенный Pi SDK
(`@earendil-works/*`) на закреплённом Node. Во время работы приложения ничего
не обновляется автоматически: новая версия SDK попадает к пользователю только
как проверенный исходный релиз Enki со всеми синхронизированными пинами.

## Единый контракт

`scripts/runtime/sdk-contract.mjs` — единственный источник проверенных значений:
версия SDK, точный Node, шесть пакетов (`pi-agent-core`, `pi-ai`,
`pi-coding-agent`, `pi-tui`, `chord`, `pi-telemetry`), хэши приватной границы
совместимости и список `qualified` (что удалённый установщик вправе ставить или
на что откатываться). Все остальные места сверяются с ним поле за полем:

| Где | Что |
| --- | --- |
| `src-tauri/resources/agent/package.json` | `dependencies` и `overrides` шести пакетов |
| `.../package-lock.json` | корень и КАЖДАЯ вложенная установка: версия, `resolved` из registry.npmjs.org, `sha512` |
| `.../runtime-lock.json` | `sdk.version`, `node.version` (его читают `build.mjs` и нативный `build.rs`), `contract`; `dataSchema` = `SCHEMA_VERSION` из `protocol.ts` (пишется в аутентифицированный `runtime-version.json`, по нему установщик сопоставляет парные копии) |
| `.../src/protocol.ts` | `SDK_VERSION`, `CONTRACT_VERSION`; `SCHEMA_VERSION` — единственный источник схемы данных (реальный `user_version` базы). `build.mjs` отказывает, если они расходятся с `runtime-lock.json`; тест `protocol.test.ts` проверяет то же и фактическую `user_version` миграций |
| `.../build.mjs` | ровно ОДНА привязка каждого пина к `runtime-lock.json` (`PINNED_SDK`, `PINNED_DATA_SCHEMA`, `PINNED_CONTRACT`), и КАЖДОЕ использование (проверка зависимостей, сверка с `protocol.ts`, метаданные `runtime-version.json`) проверяется аудитором отдельно: одна захардкоженная копия не прячется за другой ссылкой |
| `.../package.json` | `engines.node` — минимальный интерпретатор разработки = закреплённый Node (SDK сам допускает `>=22.19`, но тесты и сборка требуют точный пин) |
| `.../src/plugin-ui/sdk-ui-compat.ts` | `version` и хэши `package.json`, keybindings, theme, resource loader |
| `.../src/plugin-ui/resource-compat.ts` | берёт хэш загрузчика только из дескриптора |
| `scripts/runtime/install-remote.mjs` | принимает только `qualified` SDK/Node |
| `.github/workflows/desktop.yml`, `evaluations.yml` | `node-version` = точный Node |
| `scripts/evaluations/runner.mjs` | адаптер `pi-sdk` запускает только пакет с версией контракта |

`npm run sdk:check` печатает каждое расхождение (`файл поле: expected …, found …`)
и завершается с ошибкой. Та же проверка выполняется в начале
`runtime:prepare` — до сборки артефакта, а не при отказе нативного запуска.

## Процесс для сопровождающего

1. `npm run sdk:upgrade -- --plan --target X.Y.Z` — только литерал `X.Y.Z`
   (диапазоны, теги и `latest` отвергаются). Выводит все затрагиваемые файлы и
   поля, обязательный обзор API и гейты.
2. `npm run sdk:upgrade -- --prepare --target X.Y.Z --out /абсолютный/новый/каталог`
   на закреплённом Node (вне репозитория). В отдельном каталоге: копия
   `package.json`/`package-lock.json`, шесть пинов → цель,
   `npm install --package-lock-only --ignore-scripts` (метаданные и integrity из
   registry.npmjs.org), `npm ci --ignore-scripts`, проверка лока. Отчёт
   `upgrade-report.json`: установленная версия, `engines`, расхождения лока и
   **кандидатные** хэши дескриптора рядом с проверенными. Статус всегда
   `REVIEW_REQUIRED`: хэш — не одобрение совместимости. Репозиторий не меняется.
3. Ручной обзор: публичные типы `AgentSession`/`ModelRuntime`/UI расширений,
   поведение плагинов, контекста, ресурсов, тем и клавиш; формат JSONL сессий.
   Если upstream начал экспортировать нужное публично — перейти на публичный API.

   **Явные ресурсы Pi (проверено по реализации 0.85.1).** Enki не использует
   `DefaultResourceLoader`/`DefaultPackageManager` (они читают `~/.pi`,
   `.agents`, `settings.packages` и умеют ставить npm/git-пакеты). Загрузчик
   `plugin-ui/scoped-resources.ts` берёт только явные пути настроек:
   * навыки — публичная функция SDK `loadSkills({ skillPaths, includeDefaults:false })`;
     при совпадении имён побеждает первый путь. Порядок: общие навыки Enki
     (реестр, браузер, компьютер), затем ресурсы `packagePaths`, затем
     `skillPaths`/`promptPaths`/`extensionPaths` — как в `resolve()`
     `core/package-manager.js` 0.85.1 (пакеты собираются раньше записей
     верхнего уровня, первый выигрывает);
   * шаблоны — правила `core/prompt-templates.js loadPromptTemplates`
     (не экспортирована из индекса): прямые `.md` папки или явный файл,
     отсутствующий/битый файл — диагностика, а не отказ открытия чата;
     одноимённый более поздний шаблон проигрывает (`dedupePrompts`);
   * локальные пакеты (`packagePaths`, `plugin-ui/local-packages.ts`) — правила
     `core/package-manager.js collectPackageResources` + `core/pi-manifest.js`:
     `package.json` → `pi.{extensions,skills,prompts,themes}` (только простые
     пути внутри пакета) или папки `extensions/ skills/ prompts/ themes/`.
     Шаблоны путей, выход за пределы пакета, `npm:`/`git:` и установка не
     поддерживаются и показываются диагностикой в `GET /v1/settings/resources`.
     Строже SDK (его `collectFiles`/загрузчик навыков идут по ссылкам без
     границы и предела): граница пакета **физическая** (ссылка наружу —
     диагностика), каждая реальная папка обходится один раз (алиасы/циклы),
     обход ограничен `PACKAGE_LIMITS` (папки, записи, файлы) — при превышении
     запись не загружается целиком; вложенные `package.json` расширений
     подчиняются той же политике; папки навыков пакета раскрываются в файлы
     `SKILL.md`/`.md` самим Enki (SDK-обходчик папок их не видит). Файлы
     `.gitignore/.ignore/.fdignore` Enki не интерпретирует: запись, при обходе
     которой встречен такой файл, не загружается с диагностикой (точные файлы
     в манифесте не затронуты).
   При обновлении SDK сверить эти три места с новой реализацией и прогнать
   `src-tauri/resources/agent/test/integration/pi-resources.test.ts` (реальная активация навыков,
   шаблонов, пакета и приоритеты через раскрытие `/шаблон` и `/skill:имя`).
4. Перенести `package.json`/`package-lock.json` из staging, обновить
   `runtime-lock.json`, `SDK_VERSION`, дескриптор `sdk-ui-compat.ts` и
   `sdk-contract.mjs` (новые хэши — только после обзора). В `qualified`
   **добавить** новую пару и **оставить** предыдущую, пока к ней возможен откат.
5. Гейты: `npm run sdk:check`; `npm --prefix src-tauri/resources/agent run typecheck`;
   `npm run test:runtime` (Vitest + `test:sdk-compat`: каждый `*.node.ts` с
   реальным SDK на закреплённом Node, приватный HOME, без модели);
   `npm run test:runtime-artifact`; CI на Mac/Windows/Linux;
   репетиция удалённого обновления и парного отката.

   Как устроен `test:node` (`agent/test/run-node-suites.mjs`): до любого
   импорта SDK подгружаются `node-guard.mjs` и `setup/node-sdk-environment.mjs`.
   Guard пропускает соединение только к **живому собственному** слушателю
   этого прогона (loopback-порт или IPC-путь, зарегистрированный процессом
   прогона, включая дочерние Node-процессы, куда guard внедряется), всё
   остальное — чужие локальные порты, закрытые фикстуры, DNS и внешняя сеть —
   отклоняется и записывается; любая запись проваливает гейт, даже если
   утверждения тестов прошли. Профиль SDK — тот же неизменяемый фикстурный
   профиль, что у Vitest (`setup/sdk-profile-fixture.mjs`), и ставится
   производственным `installSdkEnvironment`, как в `main.ts`; фикстура не
   имеет права подменять `PI_CODING_AGENT_DIR`. Тестовые HTTP/SSE-клиенты
   (`helpers.ts`, `ownedRequest`) используют отдельный сокет без пула и
   закрываются с ожиданием до закрытия слушателя.

Прерванный `--prepare` оставляет только свой каталог; текущая версия, история и
настройки не затрагиваются. Неизвестная версия не может быть запущена:
нативная сторона сверяет SDK/артефакт с `runtime-lock.json`, удалённый
установщик — с `qualified`.

## Поведение обновления у пользователя и откат

* Обновление ставится только в простое: нативный/удалённый установщик берёт
  фенс обслуживания, рантайм подтверждает простой и делает **парную копию**:
  `update-backups/<id>/state.sqlite` (SQLite `backup` живой `runtime.sqlite`) и
  `update-backups/<id>/sessions/` + `sessions.json` (точные копии каждого
  изменяемого файла сессий, манифест с SHA256; хэш манифеста — в квитанции).
  Копия делается под удержанным фенсом и до того, как кандидат может открыть данные.
* Живой путь данных один: `DATA_LAYOUT` в `platform/paths.ts` (`runtime.sqlite`
  + WAL/SHM/journal + `sessions/`). Установщик получает его только из
  проверенного `daemon-control.js`; `state.sqlite` — лишь имя файла копии.
* Раскладка внутри `sessions/` тоже одна — `SESSION_LAYOUT` там же:
  `<sha16(cwd)>/<файл>` (сессии SDK, ветки, продолжения архивов),
  `<sha16>/.legacy-continuations/` (журналируемый staging продолжений: при
  копии он обязан быть пуст, иначе отказ с просьбой перезапустить — его
  разбирает восстановление при старте) и `pi-cli/pi-legacy-<48hex>/<файл>`
  (рабочие копии импортированных чатов Pi CLI: `session.jsonl`,
  `ownership.json` и файлы, созданные SDK). Манифест схемы 1 содержит только
  файлы шардов (старые копии читаются как раньше); схема 2 — также рабочие
  копии Pi CLI. Всё прочее — отказ без частичного успеха.
* Сбой кандидата: восстановление по журналу переносит текущие файлы в
  `failed-update-*` (ничего не удаляется), ставит проверенную копию БД и
  JSONL, запускает прежнюю версию. Команды, события, очереди и таймеры (в
  SQLite) и транскрипты возвращаются к одному и тому же моменту.
* Явный откат на другой SDK или схему: `install-remote-entry.mjs --rollback
  --restore-paired-data` ([удалённый хост](REMOTE-RUNTIME.md)). Без флага — отказ; без снимка сессий в квитанции
  (копия старого формата) — отказ для смены SDK. Новые данные после обновления
  сохраняются в `failed-update-*`, а не сливаются и не теряются.
* Совместимость со старыми исходниками: рантайм открывает только свои
  JSONL-файлы; оригиналы и архивы импорта (`legacy/`) неизменяемы и никогда не
  восстанавливаются поверх. Предыдущая версия получает ровно те файлы, которые
  она сама записала до обновления.

Хост-Node для `runtime:prepare`, `npm run tauri -- build` и установщика —
не ниже 22.13 (проверенный 24.22.1); точки входа (`prepare-entry.mjs`,
`install-remote-entry.mjs`) проверяют его до загрузки модулей с `node:sqlite`
и отказывают с понятным сообщением, ничего не меняя.

Каждое изменение закрепления требует новых проверок по [VERIFICATION.md](VERIFICATION.md); успешный прогон другой версии SDK не переносится автоматически.
