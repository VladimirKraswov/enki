# Обновления через Enki Hub

Начиная с 0.2.56, клиент получает релизы с настроенного Hub: тот же HTTPS origin,
публичный сертификат и ключ устройства, что у общей библиотеки. Передача истории
может быть выключена — обновления от неё не зависят. Ключи не попадают в WebView,
URL, пакеты или логи. Для первого перехода с 0.2.53 требуется новая нативная сборка.

## Ручное обновление старых клиентов

Для клиентов без поддержки Hub-обновлений доступны постоянные LAN-ссылки:

- `GET /downloads/latest/source.zip` — обычный ZIP исходников последней stable-версии.
- `GET /downloads/latest` — версия, размер, SHA256 ZIP и неизменяемая ссылка на этот снимок.
- `GET /downloads/source/{payloadSha256}.zip` — конкретный исходный снимок.
- `GET /downloads/source/{payloadSha256}.json` — его оригинальный подписанный пакет.

Например: `https://192.168.31.223:8443/downloads/latest/source.zip`.
Маршруты доступны без device/admin-ключа через существующий HTTPS listener;
только loopback и LAN, как остальной Hub. Они раскрывают исходники релиза,
которые уже публикуются в открытом GitHub, и не открывают историю, настройки,
каталог навыков, ключи либо административные API. ZIP строится из того же
опубликованного source-пакета; новый стабильный релиз автоматически меняет
`latest`, отдельная публикация ZIP не нужна. Preview не подменяет stable.
При отсутствии релиза возвращается 404. Неизменяемая ссылка позволяет скачать
точную версию после смены `latest`; SHA256 ZIP берётся из одного manifest.
Ограничение двух скачиваний также применяется к bootstrap-маршрутам.

Проверяйте локальный TLS-сертификат через известный публичный сертификат/его
SHA256-отпечаток, полученный от владельца; не отключайте TLS-проверку глобально.
После TLS-проверки сверяйте размер и SHA256 ZIP с manifest. Сам ZIP не является
новым форматом подписанного updater-пакета: его защита при ручной загрузке —
проверенный HTTPS origin и контрольная сумма. Оригинальная подпись доступна
отдельно; штатные новые клиенты по-прежнему проверяют закреплённый ключ релизов.
[Переход на Windows](WINDOWS-BOOTSTRAP.md): сборка NSIS на самом Windows,
с сохранением данных приложения и отдельным ключом устройства для Hub.

## Общий каталог моделей

`GET /api/model-catalog` (ключ устройства) возвращает общий каталог моделей: id, название
и полные определения провайдеров для OpenCode и Pi. `POST /api/model-catalog` принимает
весь каталог от администратора, проверяет схему (адреса без учётных данных, секреты
в блоки не попадают) и атомарно увеличивает версию. Настройки → «Модели (Hub)» показывают
каталог, позволяют публиковать правки и применять каталог к локальным файлам движков;
применение меняет только провайдеры, опубликованные каталогом. Выбранные модели, личные
провайдеры и ключи остаются на устройстве; списки исключений — тоже локальные.
В 2.0 применяется Pi-часть каталога к настройкам моделей Enki Runtime (ядро
перечитывает список; применение ждёт завершения работающего агента). OpenCode-часть
сохраняется в схеме для клиентов 0.2.x и в Enki 2.0 не исполняется. Без Hub обычные
и уже применённые модели продолжают работать.

## Два типа обновлений

Каждый релиз содержит два полных подписанных пакета: готовый `dist` и исходники.
Клиент сравнивает отпечаток нативных файлов, зависимостей, ресурсов, capabilities
и конфигурации. Из сравнения исключён только номер версии приложения.

- **Зелёный кружок**: нативная часть совместима. Меняется локальный интерфейс;
  Rust, Node и сборка клиенту не нужны. Основной процесс, Pi и браузер продолжают
  работать. Перед перезагрузкой UI сохраняются настройки/вложения и ожидается
  подтверждение сообщений, которые уже отправляются. Новые отправки на время
  перехода блокируются; повторной отправки истории нет.
- **Жёлтый кружок**: нужно собрать нативную часть. Клиент проверяет Node.js/npm,
  Cargo и rustc, создаёт отдельную папку из проверенного снимка и запускает `npm ci`
  и Tauri build. Сборка идёт в фоне; её можно отменить. Установка разрешена только
  после завершения собственных агентов и диалогов. Она создаёт резервную копию
  настроек, очередей, вложений и журнала доставки. Нативный перезапуск не может
  сохранить работающий внутри процесса Pi — поэтому активные задачи не прерываются,
  а установка ждёт простоя.

Наличие проверяется при запуске и каждые 5 минут, при возврате в окно, восстановлении сети и сохранении подключения Hub. Скачать, применить или назначить
установку после задач нужно явно. Кружок открывает Настройки → Обновления. Исчезновение
сервера не мешает текущей работе. Контрольная сумма и minisign-подпись с привязкой
версии проверяются до исполнения кода. Метаданные сервера сами по себе не дают
разрешения установить пакет; ключ проверки встроен в приложение.

Интерфейс обслуживается штатным локальным протоколом Tauri с прежними CSP,
capabilities, localStorage и IndexedDB. Удалённый сайт с правами Tauri не открывается.
Текущий и предыдущий интерфейсы сохраняются. Если React не подтвердит запуск за
30 секунд, происходит откат и перезагрузка только UI. Незавершённое горячее
обновление откатывается также при следующем запуске. Повреждённый/несовместимый
кэш не исполняется, используется встроенный интерфейс.

## Инфраструктура клиента

Для горячих обновлений достаточно установленной Enki. Для нативных обновлений
пользователь подготавливает [зависимости Tauri](https://v2.tauri.app/start/prerequisites/)
и Node.js/npm, Rust/Cargo, доступ к npm/crates и свободное место для сборки.
Тулчейны, компиляторы и системные пакеты в Enki не включаются и автоматически
не устанавливаются.

- macOS: Xcode Command Line Tools. Собирается `.app`; отдельный помощник ждёт
  завершения Enki, заменяет bundle и открывает новую версию. Предыдущая `.app`
  остаётся рядом с установленной. Нужны права записи в папку установки.
  Используется локальная ad hoc подпись: без Developer ID невозможно обещать
  сохранение всех разрешений macOS между нативными сборками.
- Windows: инструменты сборки MSVC, WebView2 и требования Tauri. Собирается NSIS;
  помощник после выхода приложения запускает установщик в текущую папку установки.
  Конфигурация Enki использует установку для текущего пользователя.
- Linux: зависимости WebKitGTK/GTK и Tauri. Для запущенного AppImage собирается
  AppImage, заменяется пользовательский файл. Для пакетной установки собирается
  deb либо rpm; установка вызывает штатный `pkexec` + dpkg/rpm и может потребовать
  системное подтверждение. Отсутствие polkit/системных зависимостей — явная ошибка,
  а не повод обходить ограничения ОС.

Ограничения: зависимости 15 минут, компиляция 40 минут, лог 8 МиБ; остановка
касается только созданной Enki группы процессов/Windows Job. Лог сборки остаётся
локальным, путь отображается при ошибке. Кнопка очистки удаляет только собственные
папки сборок. Истории OpenCode/Pi и внешние серверы не удаляются и не перезапускаются.
Реальный выпуск на Windows/Linux должен проходить отдельную проверку на этих ОС;
успех тестов на macOS не заменяет её.

## Окно и трей

Закрытие основного окна скрывает его и вынесенный просмотр браузера, сохраняя
агентов. Открыть приложение или страницу обновлений можно из трея; на Mac также
работает повторное открытие из Dock. Полный выход — «Завершить Enki» в трее:
интерфейс сохраняет состояние, затем штатно останавливаются собственные агенты.
Зависший UI не блокирует выход навсегда. При отсутствии системного трея окно
сворачивается, чтобы приложение оставалось доступно.

## Выпуск новой версии

Обычные `npm run build` и тесты ничего не публикуют. Официальная команда выпуска:

```sh
npm run release -- stable
# эквивалент: npm run release:hub -- stable
# либо preview
```

Изменения встроенных ресурсов браузера также запускают пересчёт нативного отпечатка при сборке.

Перед запуском: актуализировать version в package.json/package-lock.json,
Cargo.toml/Cargo.lock и tauri.conf.json, выполнить проверки, просмотреть diff и
закоммитить изменения. Команда откажется публиковать грязное дерево. Она собирает
UI, берёт только Git-tracked файлы (без .pi/.local/секретных env), подписывает оба
пакета и загружает их в Hub по compare-and-swap текущего канала. После нативного
изменения клиент сам выберет сборку; после чисто UI изменения — горячий путь.

Переменные окружения передаются через приватное окружение оператора:

- `ARVELA_HUB_URL`: HTTPS origin настроенного Hub.
- `ARVELA_HUB_CA_FILE`: публичный PEM сертификат для частного CA.
- `ARVELA_HUB_ADMIN_TOKEN`: ключ администратора, не ключ обычного устройства.
- `TAURI_SIGNING_PRIVATE_KEY_PATH`: существующий приватный ключ релизов.
- `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`: пароль ключа, если задан.
- `ARVELA_RELEASE_NOTES`: короткое описание релиза.

Не помещать эти значения в репозиторий, URL или документы. Приватный ключ никогда
не передаётся Hub и клиентам. Публикуются подписанные данные; Hub их не исполняет.
До любого обращения к Hub команда проверяет обе подписи закреплённым ключом
клиентов (`src-tauri/updater.pub`) и совпадение kind/версии/нативного отпечатка в
подписанных пакетах: пакет, подписанный другим ключом, не публикуется.
Пара интерфейс/исходники становится видимой атомарно. Команда после POST повторно
читает клиентский канал, скачивает оба подписанных пакета и сравнивает содержимое,
подписи, SHA256 и размеры с собранным релизом. Только после успешной проверки
создаётся приватная квитанция `.local/releases/<version>-<channel>.json` с Git commit
и ревизией канала. При потере подтверждения POST команда проверяет уже опубликованный релиз и не повторяет загрузку.
Для отдельных HTTPS-запросов не переиспользуются закрытые сервером соединения.
Любое расхождение завершает выпуск с ошибкой. Квитанция не
содержит ключей. GitHub/bootstrap и старый feed публикуются после подтверждённого
Hub; обычная CI-сборка не является выкаткой. Версия должна возрастать;
preview не допускается в stable. Новая версия ключа потребует доверенной нативной
миграции, подменить ключ через неподписанный ответ Hub нельзя.

## Сервер, API и восстановление

При обновлении сервиса копировать `releases.py` и `durable.py` (надёжная запись
файлов публикации) вместе с `server.py`, `memory.py`, `model_catalog.py` и `web`. Доступны авторизованные GET `/api/updates`, `/api/updates/stable`,
`/api/updates/preview`, `/api/updates/artifacts/{sha256}`; POST `/api/updates` только
администратору. До чтения большого POST проверяется авторизация; одновременно
одна публикация и две загрузки, тело до 64 МиБ. Снимок до 24 МиБ, переносимые пути,
ограничения файлов и защита от symlink/traversal. Для релизов нужно не менее 256 МиБ
свободного места сверх входящего пакета. Хранятся последние 40 артефактов и текущие
пакеты обоих каналов.

Пакеты лежат отдельно от SQLite в `<data>/releases` (`/var/lib/enki-hub/releases`;
на старой установке без каталога enki-hub — `/var/lib/arvela-hub/releases`); их нужно включать
в файловую/полную CT резервную копию. Ежедневная SQLite-копия сама по себе пакеты
не содержит. Web UI → Обновления показывает каналы, версии и размеры пакетов.
Частные локальные кэши/логи/планы установщика находятся в данных Enki
`update-runtime`; старые настройки — в `update-backups`. При сбое помощника
`last-install.json` содержит результат без секретов; предыдущая версия запускается
снова. Системная установка deb/rpm/NSIS зависит от штатных возможностей ОС.

Для read-only диагностики соединения и выбора типа обновления: запустить бинарник
Enki с `--hub-update-status`. Команда использует штатный сертификат/хранилище
ключей, не открывает окно, не собирает и не устанавливает пакеты, не трогает агентов.

Фоновая работа: на macOS 14+ в конфигурации основного WebView явно отключена
приостановка скрытого документа; при наличии Web Locks API удерживается общий
lock до выгрузки UI. Это поддерживает очереди/SSE в фоне без активного busy-loop.
Нативные агенты не зависят от таймеров WebView; сон/выключение ОС не даёт гарантии
непрерывной работы.

## Проверка выпуска 0.2.56

[Установщик для первого перехода](https://github.com/VladimirKraswov/enki/releases/tag/v0.2.56)
и совместимый старый стабильный feed опубликованы. Установленная 0.2.53 при
публикации не перезапускалась; после первого перехода обычные обновления идут
через Hub. Происходящая работа не была остановлена ради тестов.

На этой машине новая сборка и отдельный Rust TCP-клиент, запущенные из Codex,
получают EHOSTUNREACH (No route to host) к Hub; установленная 0.2.53 и Python
достигают того же HTTPS origin с тем же сертификатом. Системные журналы показывают
обновление кэша networkprivacy для bundle ID. Это согласуется с Local Network
Privacy, но не доказывает результат первого GUI-запуска новой установленной .app.
Нельзя считать живое соединение новой .app проверенным до такого запуска.

Если macOS показывает запрос, разрешите Enki локальную сеть. Проверка:
Системные настройки → Конфиденциальность и безопасность → Локальная сеть.
При запуске инструментов из IDE отдельно проверьте разрешение приложения-хоста.
Не отключайте TLS, не используйте root/proxy как обход. Apple описывает ограничения
[Local Network Privacy и стабильной подписи](https://developer.apple.com/documentation/technotes/tn3179-understanding-local-network-privacy).
Нативные сборки здесь ad hoc; надёжное сохранение идентичности между ними требует
подходящей Apple-issued signing identity, которой на этом Mac нет.

## Установленный выпуск 0.2.57

Новая версия установлена штатным GUI-запуском на macOS; установленный нативный
клиент действительно подключается к Hub и сообщает nativeVersion/releaseVersion
0.2.57. Предыдущее ограничение запуска новых бинарников из Codex не препятствует
этому установленному приложению. Изолированная старая копия 0.2.56 вне установки
по-прежнему не имеет такого подтверждения доступа — это отдельная OS-проверка.
Полный отчёт: [выпуск 0.2.57](RELEASE-0.2.57.md).

## Небольшое горячее обновление 0.2.58

Меняется только интерфейс: во время проверки кнопка показывает «Проверяю…».
Нативный отпечаток совпадает с установленной 0.2.57, поэтому клиент предлагает
зелёное обновление без сборки Rust. После применения версия интерфейса — 0.2.58,
нативная часть остаётся 0.2.57. Пользователь сам скачивает и применяет обновление.

В 0.2.59 индикатор расположен внутри нижнего блока Enki, справа от кнопки настроек.

### Каталог моделей: защита редактирования (0.2.74)

Публикация нового интерфейса передаёт `expectedVersion`; Hub возвращает HTTP409, если другой редактор уже сохранил каталог. Обновите данные и перенесите свои изменения. Старый протокол без версии пока поддерживается для совместимости. ProviderId уникален в пределах движка. Секреты в apiKey/Authorization и подобных полях должны быть ссылками на переменные/файлы, поддерживаемыми соответствующим движком, либо локальными заглушками. Пустой опубликованный каталог применяется и удаляет только ранее учтённые провайдеры Hub. Применение сначала проверяет обе конфигурации; конфликт Pi после записи OpenCode явно отмечается, владение OpenCode сохраняется для повторной попытки.

Перезапуск из настроек работает только для ещё работающего дочернего OpenCode, запущенного текущим процессом Enki, после проверки отсутствия активных задач. Сервер, найденный по порту, не считается собственным: его нужно перезапустить в средстве, которым он запущен.

Hub явно объявляет `Connection: close` для ответов, после которых закрывает сокет: клиенты не должны повторно использовать это TLS-соединение. Ответ об успешной публикации не превращается в ошибку из-за последующего сбоя кэша административного ключа.

## Публикация с подключённых устройств (0.2.104)

См. [Самодоработка](SELF-DEVELOPMENT.md). `npm run release:local -- stable`
без operator.json использует ключ устройства установленного Enki0.2.104+.
`POST /api/updates/device` доступен действующим ключам владельца и сохраняет
автора/commit/platform/аттестацию проверок в head. Подпись выполняет отдельный
Unix-socket signer, код пакета не исполняется на Hub. Отзыв ключа отменяет право
публикации. Остальные admin-маршруты остаются закрыты. Клиент сверяет оба
скачанных пакета, их хеши и подписи, и только затем пишет квитанцию.

На Hub установите minisign, скопируйте проверенные `device_updates.py`,
`release_signer.py`, `releases.py`, `durable.py`, `server.py`; разверните
`deploy/enki-release-signer.service` через `deploy/install-signer.sh` с приватным
minisign-ключом и публичным файлом. Tauri-обёртку ключа base64 предварительно
декодирует администратор в защищённом месте; не копируйте ключ клиентам.
HTTP-пользователь не должен владеть кодом службы или читать каталог ключа.
Старый закреплённый ключ сохранён. Ключ централизованной подписи теперь онлайн;
считайте эту службу частью доверенной инфраструктуры и её защищённых backup.
