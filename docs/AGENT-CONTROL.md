# Управление Enki через MCP

Enki предоставляет локальный API управления для Codex и других MCP-клиентов. Агенту не требуется двигать физическую мышь, распознавать
интерфейс по снимку или редактировать `localStorage` приложения.

## Подключение

1. Запустите установленный Enki. На macOS/Linux при старте создаётся Unix-сокет и
   descriptor `~/.local/share/enki/agent-control/control.json` (Linux учитывает
   `XDG_DATA_HOME`). Каталог имеет режим `0700`, сокет и файл — `0600`. На Windows
   используется случайный порт только `127.0.0.1`, descriptor в данных Enki
   текущего пользователя. Во всех случаях descriptor содержит случайный
   256-битный токен процесса; работайте через MCP, не передавайте его агенту.
2. В приложении откройте **Настройки → API для агентов → Подключить MCP**. Enki
   сохранит запись `enki-control` в собственном общем реестре MCP. Она загрузится
   в новых чатах встроенного Pi SDK. Регистрация доступна на локальном
   компьютере после завершения работающих агентов; чужая запись с таким
   идентификатором не перезаписывается. Внешние конфигурации не изменяются.
   Первичную регистрацию также можно выполнить инструментом
   `desktop_install_mcp` уже запущенного отдельного MCP-процесса.
3. В любом другом MCP-клиенте используйте установленный бинарник:

   ```json
   {
     "mcpServers": {
       "enki-control": {
         "command": "/Applications/Enki.app/Contents/MacOS/enki",
         "args": ["--agent-mcp"]
       }
     }
   }
   ```

   На Linux укажите путь к установленному `enki`. Режим MCP не
   создаёт второе окно и не запускает второе ядро Enki Runtime.

## Рабочий цикл агента

1. `desktop_status` — проверить подключение, выбранные проект/чат/модель и
   незавершённые запросы пользователя.
2. `desktop_projects`, затем `desktop_sessions` — получить реальные идентификаторы.
3. `desktop_new_chat` либо `desktop_select` — выбрать точное место работы.
4. При необходимости `desktop_configure` — выбрать доступную модель, variant и
   агента. Политика разрешений этим API не повышается.
5. `desktop_send` вызывается один раз. Его ответ означает только принятие задачи.
   Для длительной задачи задайте `completion_marker`, `max_continuations` и,
   желательно, `checkpoint_path`. Полный контракт описан в
   [AGENT-FACTORY.md](AGENT-FACTORY.md).
6. `desktop_wait` ждёт `idle`, `needs_input`, `failed` или bounded timeout. Для
   задач, отправленных именно через `desktop_send`, Desktop также распознаёт
   редкий сбой локальной модели: завершённый ответ содержит текстовый
   `<tool_call>`, но ни одного настоящего tool-part. В этом случае он до двух
   раз просит модель повторить тот же шаг настоящим встроенным инструментом и
   продолжает ожидание. Управляемая длительная задача также не считается
   завершённой без точного маркера приёмки и получает ограниченные продолжения
   с checkpoint. После двух синтаксических неудач возвращается
   `recovery_exhausted`, а не ложный успешный `idle`.
   Явный `desktop_stop` немедленно завершает все совместные ожидания этой
   сессии с исходом `stopped`.
7. При `needs_input` прочитать `desktop_interactions`. Разрешения `once/always`
   допустимы только после явного решения пользователя; без такого решения можно
   только ждать или отклонить запрос. Ответы на вопросы нельзя выдумывать.
8. `desktop_conversation` возвращает ограниченную нормализованную историю и
   является источником финального результата.
9. `desktop_managed_runs` показывает незавершённые длительные контракты после
   перезапуска. `desktop_forget_managed_run` безопасно снимает автопродолжение,
   не останавливая и не удаляя сессию Enki.

`desktop_stop` останавливает конкретную сессию. Ожидание не блокирует status,
просмотр взаимодействий или stop из другого клиента. `desktop_set_view` открывает
панели приложения без pointer automation. Все команды сериализуются и проходят
через тот же frontend store, поэтому состояние MCP совпадает с видимым UI.

## Граница безопасности

- Listener — Unix-сокет текущего пользователя на macOS/Linux либо случайный
  loopback TCP-порт на Windows. LAN-порт не открывается; CLI проверяет,
  что адрес из Windows descriptor — именно 127.0.0.1. Токен обязателен для каждого запроса.
- На один запрос принимается не более 1 MiB, ответ ограничен 8 MiB, команда —
  шестью минутами, ожидание модели — пятью минутами за один вызов. Одновременно
  принимается до 32 соединений; незавершённый вход закрывается через 10 секунд.
- MCP не выдаёт shell и не меняет файлы напрямую. Файловые операции выполняет
  встроенный агент Pi SDK в рамках разрешений сессии Enki.
- Автовосстановление не действует на обычные UI-сессии, пользовательский текст,
  незавершённые ответы или корректные tool-parts. Оно не отвечает на вопросы и
  не подтверждает разрешения; `needs_input` всегда передаётся человеку.
- Контракт длительной задачи хранится отдельно от transcript, разделён по
  серверу, ограничен по числу записей/сроку и переживает перезапуск Desktop.
  Prompt, tool output и credentials в это хранилище не попадают.
- Сохранённые архивы прежних движков доступны для чтения. Продолжение создаётся
  проверенным переносом в Pi SDK; старые сообщения и инструменты не выполняются
  повторно. Модель внутри рабочей сессии выбирается независимо от её архива.
- При закрытии Desktop descriptor и сокет удаляются. После аварийного завершения
  старый descriptor безопасно заменяется новым при следующем старте.

## Таймеры сессий

`desktop_schedule` управляет разовыми и повторными пробуждениями. Отдельный
общий MCP `enki-schedules` запускает `--schedule-mcp`, который открывает только
этот инструмент. Остальные команды управления через него недоступны.
[Режимы, сохранение и ограничения](SCHEDULES.md).

## Диагностика

- `Enki control endpoint was not found` — приложение не запущено.
- `still starting` — WebView ещё не установил обработчик; повторите через секунду.
- `cannot connect` — descriptor остался от аварийно завершённого процесса;
  перезапустите Desktop.
- MCP подключён, но задача требует разрешения — это штатный `needs_input`, а не
  зависание. Откройте запрос в Desktop или передайте явный ответ через MCP.
