# Agent Factory: длительные задачи локальных моделей

Agent Factory — это режим над существующими чатами среды выполнения Enki, а не
второй агентский движок. Ядро Enki (Pi SDK) по-прежнему владеет transcript,
инструментами, разрешениями, compaction и вызовами модели. Приложение добавляет
только проверяемый и ограниченный жизненный цикл длительной задачи.

## Какие сбои он закрывает

- Ошибочно напечатанный как текст tool-call распознаётся и повторяется не более
  двух раз.
- Досрочный обычный `stop` не считается успехом, если отсутствует заданный
  вызывающей стороной маркер приёмки.
- Сессия может получить до заданного числа сообщений «продолжай с checkpoint».
- Контракт и счётчики переживают перезапуск Enki. Transcript при
  этом не копируется: он остаётся в истории чата ядра.
- `needs_input`, ошибка, timeout, исчерпание повторов и успешное завершение —
  разные исходы. Никакой из них не подменяется зелёным `idle`.

Система не пытается семантически угадать, готов ли произвольный код. Для этого
запускающий агент обязан задать буквальный `completion_marker`, а исходная
задача — наблюдаемые критерии приёмки. Маркер принимается только отдельной
точной строкой ответа ассистента.

## Запуск

Вызовите `desktop_send` с обычными параметрами и тремя полями управления:

```json
{
  "directory": "/path/to/project",
  "text": "Реализуй этап и прогони перечисленные проверки...",
  "completion_marker": "GUI_STAGE_2_ACCEPTED",
  "max_continuations": 8,
  "checkpoint_path": ".pi/TASK.md"
}
```

`completion_marker` состоит из ASCII-букв, цифр, `.`, `:`, `_`, `-` и имеет
длину до 128 символов. `checkpoint_path` — безопасный относительный путь без
`..`; содержимое checkpoint не хранится в Desktop. `max_continuations` ограничен
диапазоном 0–20, по умолчанию 6 при наличии маркера.

Desktop добавляет к исходному prompt контракт работы: использовать инструменты,
обновлять checkpoint на значимых этапах, после compaction перечитывать его,
задавать человеку штатные вопросы и печатать маркер только после реальной
проверки критериев. Затем вызывающая сторона повторяет `desktop_wait`.

## Состояния

- `completed` — точный маркер найден отдельной строкой; запись управления удалена.
- `idle` — обычная неуправляемая задача завершилась.
- `needs_input` — ожидается человек; автоматического ответа нет.
- `failed` — ядро сообщило неуспешный исход хода (ошибка модели, обрыв по лимиту
  длины, ход без ответа и т. п.).
- `stopped` — явная остановка немедленно отменила активное ожидание.
- `timeout` — текущий bounded wait закончился; задача и её контракт сохранены.
- `incomplete` — маркера нет и лимит продолжений исчерпан.
- `recovery_exhausted` — два исправления malformed tool-call не помогли.
- `recovery_failed` — ядро не приняло служебное продолжение; автоматический
  запуск позже запрещён.

`desktop_status.managedRun` показывает маркер, checkpoint и использованные
лимиты активной сессии без prompt, вывода инструментов или секретов.
`desktop_managed_runs` возвращает такой же безопасный список для текущего
сервера. `desktop_forget_managed_run` снимает только контракт продолжения, не
останавливая и не удаляя сам чат; `desktop_stop` останавливает чат и также
снимает контракт.

## Безопасность и ограничения

- Режим включается только явным `completion_marker`. Обычные UI-чаты и обычный
  `desktop_send` не получают семантических продолжений.
- Каждый retry ограничен, записан в transcript и запускается только во время
  явного `desktop_wait`; скрытого фонового цикла нет.
- Следующее продолжение разрешается только после финального ответа ассистента
  на предыдущую отправку. Временный `idle` и промежуточный `finish=tool-calls`
  не считаются границей хода и не создают дублирующий prompt.
- Параллельные `desktop_wait` для одной сессии объединяются в одно наблюдение,
  поэтому два MCP-клиента не могут одновременно отправить два продолжения.
- Разрешения и structured questions никогда не подтверждаются автоматически.
- `desktop_stop` окончательно удаляет контракт автопродолжения.
- `desktop_stop` также немедленно отменяет все объединённые ожидания этой
  сессии; они возвращают `stopped`, а не висят до timeout.
- Записи разделены по серверу и session ID, ограничены 100 элементами и живут
  не более 30 дней. Хранятся только метаданные управления.
- Выключенный компьютер не исполняет задачу. После запуска Desktop внешний
  супервизор должен снова вызвать `desktop_wait`; состояние уже будет восстановлено.

## Рекомендуемый prompt для слабой локальной модели

Исходная задача должна содержать: один конкретный результат, запреты и границы,
порядок этапов, точные команды проверки, требуемые доказательства и правило не
объявлять готовность при незакрытом пункте. Большой roadmap следует делить на
этапы, каждому давать собственный маркер. Это уменьшает потерю цели после
compaction и делает ошибку локальной, а не обнуляющей многосуточный прогон.
