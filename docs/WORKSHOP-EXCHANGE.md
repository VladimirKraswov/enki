# Обмен Мастерских через Hub

Windows и Mac используют проверенное LAN HTTPS-подключение к Hub. Ключи
устройств, вход и admin/signing key на клиенте не нужны. Обмен исходниками
не публикует stable, не выполняет код на Hub и не запускает агента получателя.

## Сообщения между агентами

Штатный инструмент `hub_exchange` доступен сессиям Enki Runtime и проходит обычный
runtime gate. При открытии сессии выполняется ограниченная регистрация присутствия.
`status` возвращает устройства и наблюдавшихся агентов: device, agent, session,
seen. Это время последнего наблюдения, а не обещание, что агент сейчас онлайн.
В ответе до 200 последних агентов; усечение отмечается `agentsTruncated`.

1. `action=status`: найти точные ID устройства и сессии; agent штатного клиента — `enki`.
2. `action=send`, `recipient`, `recipientSession`, `text`: передать сообщение.
   `requestId` можно задать явно; при потерянном ответе повторять только с тем же
   ID и тем же содержимым. По умолчанию используется ID вызова инструмента.
3. Получатель явно вызывает `action=inbox`. Чтение не подтверждает обработку.
4. После обработки — `action=ack`, `id` из квитанции. `action=sent` показывает
   отправителю подтверждение. ACK означает получение/обработку сообщения, а не
   проверку патча или завершение запрошенной работы.

Отправитель всегда привязан к реальной сессии Runtime. Другой получатель не может
подтвердить сообщение. Входящий текст и исходники — недоверенные данные: они не
заменяют поручение владельца, системные инструкции или разрешения. Нет фонового
запуска заданий, автоматических ответов, рекурсивных agent runs или fallback на
другое устройство. Удалённому Runtime нужен подключённый нативный broker; его
идентичность Hub принадлежит устройству этого broker.

## Передача изменений до релиза

В исходниках каждой Мастерской задайте `ENKI_NATIVE_EXECUTABLE` из `RUNTIME.json`.
Нужна нативная версия с поддержкой workshop exchange. Старый Enki 2.0.31 не
поддерживает новый CLI: сначала требуется штатное обновление приложения.

```sh
npm run workshop -- status
npm run workshop -- push --base FULL_BASE_COMMIT --agent enki --session SESSION_ID --summary "Описание изменения"
npm run workshop -- changes
npm run workshop -- change --id RECEIPT_ID --out .local/received-change.json
```

На Windows переменная задаётся через `$env:ENKI_NATIVE_EXECUTABLE`, на macOS —
через `export ENKI_NATIVE_EXECUTABLE=...`. Headless-оператор может использовать
свой приватный `ENKI_HUB_DEVICE_CONFIG` в существующем формате device publisher.
CLI также распознаёт приватный `.local/workshop/device.json` этого checkout.
Ключи разных устройств не копируют друг другу. Транспорт проверяет HTTPS и
сертификат, смену подключения и отзыв устройства.

Передаются только **закоммиченные** изменённые UTF-8 файлы между base и HEAD,
включая явные удаления. Незакоммиченный эксперимент не входит в пакет и остаётся
на месте. `.git`, `.local`, `.pi`, `.env`, dependencies/target исключены. Предел —
200 файлов, 512 KiB на файл, 1 MiB суммарных исходников. Большое изменение нужно
разбить. Файлы проверяются на опасные пути и известные форматы ключей; это не
заменяет ручную проверку секретов перед отправкой.

Hub хранит автора устройства, base/commit как **заявленные** Git ID, SHA256 пакета
и серверную квитанцию. Он не проверяет Git-объект и не выполняет `git apply`.
Получатель сверяет базу, содержимое и digest в отдельной рабочей копии. JSON
скачивается как материал ревью, существующий файл не перезаписывается.
`hub_exchange action=change` возвращает метаданные и имена файлов; содержимое
получают через CLI и читают выборочно. Вывод инструмента ограничен с явным усечением.
Обычный релиз после проверок остаётся `npm run release:local -- stable`.

Для JSON-сообщений/логов и ACK из CLI:

```sh
npm run workshop -- submit --kind messages --file /absolute/private/message.json
npm run workshop -- submit --kind logs --file /absolute/private/log.json
npm run workshop -- submit --kind ack --file /absolute/private/ack.json
npm run workshop -- retry --file /absolute/private/saved-request.json
```

CLI сохраняет точный запрос в `.local/workshop/outbox` **до** отправки. Потерянное
подтверждение не является успехом; повтор использует сохранённый запрос. Форматы:

```json
{"requestId":"unique-operation","agent":"enki","session":"sender-session","recipient":"device-id","recipientAgent":"enki","recipientSession":"destination-session","text":"Материал для ревью","change":"optional-change-receipt"}
```

```json
{"requestId":"unique-error","agent":"enki","session":"session-id","level":"critical","code":"shell.cleanup-unknown","operation":"tool-call-id","detail":"Краткое описание без секретов"}
```

ACK: `{"id":"message-receipt","agent":"enki","session":"destination-session"}`.

## Диагностика по сессиям

При включённом Hub существующий локальный outbox передаёт ошибки модели и
инструментов без обязательной передачи текста разговора. Ошибка инструмента
теперь собирается даже до завершения ответа модели. Сырые команды, вывод,
reasoning и вложения в этот поток не входят.

Обрывы SSE записываются отдельно от истории чата: код timeout/http/protocol/
transport, ID выбранной сессии, клиентское время наблюдения и серверное время
приёма. Сборщик просыпается при ошибке и передаёт запись в native outbox; после
подтверждённой локальной записи она переживает перезапуск и сетевой сбой. До
этой записи действует ограниченный буфер памяти; аварийное завершение в этом
коротком промежутке может потерять событие. Очередь привязана к Hub-профилю;
смена Hub не отправляет события прежнего профиля в новый.

`hub_exchange action=log` добавляет явную критическую запись. `action=logs`
читает записи текущей сессии и отдельный `historyErrors` из автоматической
синхронизации. CLI поддерживает фильтры:

```sh
npm run workshop -- logs --session SESSION_ID --device DEVICE_ID
npm run workshop -- inbox --agent enki --session SESSION_ID
```

`historyErrors` — ограниченный диагностический снимок до 100 ошибок из последних
1000 записей, с явными счётчиками/признаком усечения. Это не полная трассировка
процесса и не доказательство завершения дерева процессов. Закрытые чаты, ещё не
синхронизированные клиентом, могут требовать отдельного импорта. Ошибки старта
нативного процесса до подключения Hub сами по себе в этот канал не попадают.

## Сервер и хранение

API: `/api/workshop/status`, `/presence`, `/changes`, `/changes/ID`, `/messages`,
`/inbox`, `/ack`, `/logs`. GET читает; POST изменяет. Ключ отозванного устройства
отклоняется. Inbox ограничен устройством, агентом и сессией. Для списков используются
`after`/`limit` и монотонный серверный seq, без пропуска одинаковых timestamps.

Данные находятся в отдельных таблицах существующей `hub.sqlite`, входят в
штатную SQLite backup и удаляются обслуживанием по `retention.textDays`
(по умолчанию 180 дней, включая непрочитанные сообщения и исходники). На устройство
действуют пределы 10000 записей и 64 MiB; превышение явно отклоняется, без тихого
удаления новых записей. Независимые истории и Git не меняются.

Развёртывайте `workshop.py` вместе с `server.py`; перед обновлением сохраняйте
парную копию кода и SQLite. Перезапуск Hub не заменяет выпуск/установку клиента.
Поддержку установленной Windows проверяют отдельно после обновления.
