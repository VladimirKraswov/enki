# VM 5200 final audit and retrospective — 2026-11-14

This is the operational snapshot after the cleanup and NUMA refactor. It is a
narrow, measured configuration, not a general-purpose inference platform.

## Final host topology

| Resource | Inference VM 5200 | Host and other services |
| --- | --- | --- |
| CPU | all 40 threads of NUMA node 0 (`0-19,40-59`) | NUMA node 1 (`20-39,60-79`) |
| RAM | 236 GiB allocated, 231 GiB visible | node 1: ~93 GiB free |
| QEMU memory placement | node 0 only; measured `N0=236.1 GiB`, `N1=0` | other VMs pinned to node 1 |
| GPU | RTX 5090, 32 GB | V100 VM stopped (`onboot: 0`) |
| Guest disk | 703 GB free | host thinpool 89.44% |

`oracle`-like assumptions are avoided: the VM has one guest NUMA node, so the
host placement is enforced by QEMU and the systemd `NUMAPolicy=bind, node0`
masks. No node-1 page is used by active inference.

Both inference units have `CPUAffinity=0-39`, `NUMAPolicy=bind`,
`NUMAMask=0`, `StartLimitIntervalUSec=0`. They are allowed the full node but are
never active together; no CPU is partitioned between Qwen and Ornith.

Qwen API currently reports `status.value=unloaded`. Infernix is the active engine.

## Switching

- Cold Qwen after VM boot: **112 s**.
- Warm Ornith → Qwen: **50 s**.
- Warm Qwen → Ornith: **58 s** (Infernix reloads 68 GiB of weights and state).
- Gateway resets failed state before every start. The old systemd start rate
  limit was a real defect for a model that is intentionally restarted on every
  switch; it is disabled.

There is no suspend/resume or detachable CUDA context. A switch is a process
restart. Extra RAM improves page-cache retention but does not remove the reload.

## Measured speed (thinking off, same prompts)

| Model | Short median | Short max | ~52K context |
| --- | ---: | ---: | ---: |
| Qwen3.8-Flash-Next | 101.1 | 110.6 | **115.3 tok/s** |
| Ornith Infernix NVFP4 | 54.9 | **63.6** | 52.1 tok/s |

At ~6.4K prompt, Infernix prefills faster (1,801 vs 1,332 tok/s). At ~52K,
Qwen prefills slightly faster (4,223 vs 3,984 tok/s) and decodes much faster.
These are RTX 5090 + E5/DDR4/PCIe 3 measurements, not the author's i9/DDR5/PCIe5
numbers.

## Retrospective

1. **Full model files do not imply a fast switch.** Qwen and Infernix have
   separate processes, pinned allocations and CUDA state. Both cannot be active
   on one 32 GB GPU.
2. **The hardware bottleneck was not only VRAM.** Infernix's default six CPU
   workers measured 4,417 experts/s on this E5. Raising the team to 24 restored
   ~47 tok/s; the default author's tuning was too conservative for this CPU.
3. **MTP tuning matters.** Fixed three drafts beat auto=2 and DFlash2 on this
   workload; all tested variants produced identical hashes, so no quality
   shortcut was introduced.
4. **NUMA locality matters.** Putting part of VM memory on node 1 dropped
   Infernix decode from ~47 to ~40 tok/s. The final VM is entirely node 0.
5. **Page cache is not always controllable.** Infernix uses O_DIRECT for direct
   artifact reads; a node-1 vmtouch cache was removed as ineffective.
6. **Start limits and auto-start are production bugs here.** `strata-gateway`
   used to start Qwen at boot; it now does not. Repeated intentional switches
   must not trip systemd's start-rate limit.
7. **Do not split CPU between models that never run together.** Both services
   receive the full node-0 mask; only the active engine consumes it.

## Refactoring delivered

- Gateway startup/switch now resets failed state and uses `--no-block` plus a
  readiness wait; unreachable Qwen is `False`, not a thrown exception.
- Gateway model-progress path uses the real Infernix directory and both
  `.gguf`/`.infernix` suffixes; old Q4 paths were removed.
- Qwen and Infernix units have explicit CPU/NUMA masks and no start rate limit.
- Qwen readiness uses the current Control Python after the old venv removal.
- Legacy watchdog, PolyStrata, llama.cpp, old Strata builds and test caches were
  removed from the VM.

## Not to do

- Do not start V100 until the owner explicitly asks; its 16 GiB config is
  stopped and reserves nothing.
- Do not place inference memory on node 1 or increase Infernix workers without
  measuring; 24 is the plateau with engine headroom.
- Do not use `--a8-activations` or `--expert-tail-skip` for “speed” without a
  separate quality A/B.
- Do not publish a Desktop release for these server-only changes; public model
  IDs and URLs did not change.

## Known limitations

- The first Qwen start after a VM reboot is cold (~112 s); later warm cycles are
  ~50 s because the arena remains unloaded/resident.
- Infernix is a third-party hobby/AI-generated engine with an explicit upstream
  disclaimer; source and artifact are pinned and SHA-checked.
- The host thinpool is at 89.4% and must not receive another large duplicate.
- Remote mobile/PWA and real Windows acceptance are separate from this audit.
